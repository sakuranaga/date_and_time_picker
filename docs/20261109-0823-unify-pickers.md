# 3つのピッカーのコード共通化（DP-0010）

- ステータス: Reviewed
- 課題: LAP DP-0010「datepicker / timepicker / datetimepicker のコード重複を解消する」
- 作成: 2026-11-09
- 前提: DP-0015（テスト基盤と特性テスト 58件）がマージ済み

## 1. 目的

`datetimepicker.js` は `datepicker.js` と `timepicker.js` をほぼコピーしたもので、同じロジックが2〜3か所にある。
このままでは残りの修正（DP-0001〜0009、0011〜0014）を2〜3回ずつ入れることになり、漏れが出る。
修正の前に、ロジックを1か所にまとめる。

## 2. 仕様（変えないこと）

**振る舞いは一切変えない純粋なリファクタリング**とする。既知のバグもそのまま残す（各課題で直す）。

維持するもの:

- 公開 API: クラス名 `DatePicker`・`TimePicker`・`DateTimePicker`、IIFE のグローバル
  （`window.DatePicker.DatePicker` など。各エントリが export するのはそのクラス1つだけ）、
  コンストラクタの引数、static `instances`（クラスごとに別の配列）、`destroy()`、TimePicker の
  `setValue()`・`getValue()`・`openPicker()`・`closePicker()`・`scrollToItem()`・`static closeAllPickers()`
- 自動初期化のセレクタと data 属性（`.date-picker-wrapper`、`.tp-input`、`data-min-date` など）
- 生成する DOM（要素・クラス名・属性・順序）。CSS とその変数（`--dp-*`、`--tp-*`）。
  ただし、要素の間の**空白だけのテキストノード**（テンプレート文字列のインデント）は変わってよいものとする。
  ピッカー内の該当箇所はすべて block・flex・grid のコンテナで、空白だけのテキストノードは表示に影響しない
- input の値と `change` イベントの回数・順序、`.dp-overlay` の共有（クラスをまたいで1つ、破棄の判定は各クラスの中だけ）
- `dist/` の3ファイルの役割とファイル名、`holiday.csv` の読み込み

## 3. スコープ

### やること

- 純粋なロジックを関数として `core/` に切り出す（DP-0015 で後回しにした「関数として切り出す」もここで行う）
- DatePicker と DateTimePicker の本体を1つのクラスにまとめる
- 時刻の列（時・分の項目の生成、選択、スクロール）を DateTimePicker と TimePicker で共有する部品にする
- 自動初期化と祝日 CSV の読み込みを共有する
- 切り出した関数の単体テスト、DOM と公開 API が変わらないことを確かめるテスト

### やらないこと

- バグ修正（各課題で行う）。たとえば分の丸め（DP-0002）は今の計算のまま関数に移す
- TimePicker の DOM を DateTimePicker の time モードの DOM（`.dp-*`）に置き換えること。
  `.tp-*` のクラス名と `--tp-*` 変数で見た目を変えている利用者がいる前提で、互換のため TimePicker の外枠は残す
- CSS の共通化（`datepicker.css` と `datetimepicker.css` の重複）。JS の重複とは別の話なので、必要なら別の課題にする
- 未使用コードの削除（DP-0014 で行う。`scrollToItem` などはそのまま残す）

## 4. 設計

### 4.1 ファイル構成

```
core/
  date-utils.js     純粋関数: 日付オプションの解釈、範囲判定、同日判定、祝日キー、日付の整形、月の42マス
  time-utils.js     純粋関数: 時の値、分の値（刻み）、現在時刻からの初期値、入力値からの時・分の取り出し
  holidays.js       祝日 CSV の解析、スクリプトの場所の解決、CSV の取得
  time-columns.js   class TimeColumns: 時・分の列の生成・選択・選択解除・スクロール（クラス名は引数で受け取る）
  picker-core.js    class PickerCore: 今の DateTimePicker の本体（mode: date / time / datetime）
  auto-init.js      .date-picker-wrapper の自動初期化（祝日を読んでからインスタンスを作る）
datepicker.js       CSS を import、class DatePicker extends PickerCore（mode は date 固定）、自動初期化
datetimepicker.js   CSS を import、class DateTimePicker extends PickerCore、自動初期化（mode・minuteStep も読む）
timepicker.js       CSS を import、class TimePicker（外枠・overlay・API は今のまま、列は TimeColumns、計算は time-utils）
```

- rollup の入力（3つのエントリ）は変えない。`core/` はエントリから import され、各バンドルに取り込まれる。
- エントリが export するのはクラス1つだけ。`PickerCore` などを export すると IIFE のグローバルに余計なプロパティが増えるので、
  エントリからは export しない。

### 4.2 core/date-utils.js

今の `parseDate`・`isDisabled`・`isSameDay`・`isHoliday` のキー・`setInputValue` の整形・`updateCalendar` のマス計算を、
処理を変えずに関数にする。

```js
export function parseDateOption(value, now = new Date())   // null | 'today' | Date | 'YYYY-MM-DD' | Date で解釈できる文字列
export function startOfDay(date)                            // 時刻を 0:00:00.000 にした新しい Date
export function isOutOfRange(date, min, max)                // 今の isDisabled と同じ（日単位、両端を含む）
export function isSameDay(a, b)
export function holidayKey(date)                            // 'YYYY/M/D'
export function formatDate(date, format)                    // 'YYYY'・'MM'・'DD' を1回ずつ置き換える（今の実装のまま）
export function buildMonthCells(year, month)                // [{ date, otherMonth }] を42件（前月の残り・当月・翌月）
```

### 4.3 core/time-utils.js

```js
export const HOURS                                  // ['00', ..., '23']
export function minuteValues(step)                  // 0 から step 刻みで 60 未満（step の検証はしない。DP-0005 で行う）
export function nearestTime(now, step)              // { hour, minute }。今の丸めの式のまま（繰り上がらないのは DP-0002 で直す）
export function matchTimeValue(value, mode)         // DateTimePicker の解釈: time は /(\d{2}):(\d{2})/、datetime は末尾の /(\d{2}):(\d{2})$/
export function splitTimeValue(value)               // TimePicker の解釈: value.split(':') の [hour, minute]
```

- DateTimePicker と TimePicker で入力値の解釈が少し違う（正規表現と split）。今の振る舞いを変えないため、
  それぞれの関数を残し、どちらを使うかは呼ぶ側で決める。
- 「値があれば解釈し、取れなければ現在時刻」という流れも、両者で少し違う
  （DateTimePicker は時・分の両方が取れなければ現在時刻、TimePicker は値があれば取れた方だけ選ぶ）。これも呼ぶ側に残す。

### 4.4 core/time-columns.js

```js
export class TimeColumns {
  constructor(hourColumn, minuteColumn, classes, step)
  // classes: { item, hourItem, minuteItem }（例: TimePicker は tp-item / tp-hour-item / tp-minute-item、
  //          PickerCore は dp-time-item / dp-hour-item / dp-minute-item）
  render()                    // 今と同じ HTML（data-value・role="option"・tabindex="-1"）を各列に入れる
  select(kind, value)         // kind: 'hour' | 'minute'。selected クラスと aria-selected を付け替える
  clearSelection()            // DateTimePicker のクリアボタンの処理
  scrollToSelection()         // 今の scrollToSelection / scrollToTimeSelection と同じ計算を両方の列に
  scrollToItem(column, value) // TimePicker の scrollToItem と同じ計算
  itemFrom(target, kind)      // クリックされた要素が kind の項目なら、その値を返す
}
```

- 列の外枠（`.tp-container` と `.dp-time-container` など）は今のまま各クラスが作り、TimeColumns は中身だけを扱う。
- 選択状態（`selectedHour`・`selectedMinute`）と input への書き込みは、今のまま各クラスのプロパティとメソッドに残す
  （`selectHour()`・`selectMinute()` は TimeColumns を呼んでから今の処理を続ける）。

### 4.5 core/picker-core.js

今の `DateTimePicker` クラスをそのまま移し、上の関数と TimeColumns を使う形にする。違いは2点だけ。

1. static `instances` の持ち主（公開クラス）をコンストラクタの引数で受け取り、`this._registry.instances` で参照する。
   DatePicker は `DatePicker` を、DateTimePicker は `DateTimePicker` を渡す。今のコードは公開クラスの配列を直接参照しているので、
   利用者が `class X extends DatePicker { static instances = [] }` としても、X のインスタンスは `DatePicker.instances` に入る。
   `this.constructor.instances` にするとこれが X 側の配列に変わってしまうため、持ち主は公開クラスに固定する。
   配列は参照のたびに `registry.instances` から読む（差し替えられても追従する）。「他のピッカーを閉じる」「overlay を隠すか」の
   判定は、今と同じく同じクラスのインスタンスだけを見る。
2. dialog の `aria-label` を引数で受け取る（DatePicker は 'Date Picker'、DateTimePicker は 'DateTime Picker'。今と同じ値）。

DatePicker と DateTimePicker（date モード）の違いは、今のコードでは次の2つしかなく、どちらも振る舞いは同じ:
- クリアボタンの無効判定（`!selectedDate` と `!selectedDate && selectedHour === null`）。date モードでは `selectedHour` は常に null なので同じ。
- `aria-label`。上の 2 で対応する。

```js
// datepicker.js
export class DatePicker extends PickerCore {
  static instances = [];
  constructor(wrapper, options = {}) {
    super(wrapper, { ...options, mode: 'date' }, { registry: DatePicker, ariaLabel: 'Date Picker' });
  }
}
```

- DatePicker は今 `mode` オプションを持たないので、渡されても date に固定する（今は無視される＝date と同じ）。
- `minuteStep` も DatePicker では使われない（今と同じ）。

### 4.6 core/holidays.js と core/auto-init.js

- `parseHolidayCsv(text)`・`resolveBasePath(document)`・`loadHolidays(url)`（fetch が失敗・非 2xx なら空の Set）は、今の2ファイルの実装と同じ。
- `resolveBasePath` は `document.currentScript` を使うので、**エントリのトップレベルで同期的に**呼ぶ（今と同じタイミング）。
  `autoInit(PickerClass, readOptions, basePath)` の引数で渡す。
- `readOptions(wrapper)` は各エントリが持つ（DatePicker は min/max/format だけ、DateTimePicker は mode と minuteStep も。今と同じ）。
- DOMContentLoaded を待つ処理も今と同じ。

### 4.7 timepicker.js

- 外枠（popup・global overlay と、そのクリックで全部閉じる処理）、`isOpen`・`justOpened`、イベント登録（focus で開くことを含む）、
  公開メソッドは今のまま残す。
- 時・分の列の生成・選択・スクロールは TimeColumns、現在時刻からの初期値は `nearestTime`、値の解釈は `splitTimeValue` を使う。

### 4.8 バンドルへの影響

- `dist/datepicker.js` には PickerCore を通して時刻の列のコードも入るので、数 KB 大きくなる見込み（今 14,951 バイト）。
  機能は変わらない。サイズは実装後に記録する。
- `dist/timepicker.js` には core の一部（time-utils と TimeColumns）だけが入る。

## 5. テスト方針

- **振る舞いの同一性**: DP-0015 の特性テスト 58件を**変更せずに**すべて通す。これが最も重要な受け入れ条件。
- **振る舞いの記録との比較（新規・先に書く）**: 共通化の前に、今のコードでシナリオを流して「記録」を作り、
  `tests/fixtures/golden/*.json` に保存する。共通化の後のコードで同じシナリオを流した記録が、これと完全に一致することを確かめる。
  - 記録する内容（各操作の後）: ピッカーの DOM（`outerHTML`。空白だけのテキストノードは除き、TimePicker の Math.random 由来の `id` は固定の文字列に置き換える）、
    input の `value`、その操作で発火した `change` の回数と、そのときの値の並び、開閉の状態、overlay の状態、フォーカスのある要素。
  - シナリオ: DatePicker、DateTimePicker の date / time / datetime、TimePicker のそれぞれで、開く → 日付を選ぶ → 開き直す → 月の移動 →
    時・分を選ぶ → クリア → Esc / 外側クリック → 別のピッカーを開く → destroy。時刻の値の解釈の違いを含める
    （TimePicker と DateTimePicker(time) に `'08:30'`、`'8:5'`、`'08:30:00'`、`'abc'` を入れて開く）。時刻は mock timers で固定。
  - **この記録は既知のバグの振る舞いも含む**（例: 開いたときの change が2回）。共通化で振る舞いが変わらないことを見るための一時的な基準で、
    各バグ修正でその部分の記録が変わるのは期待どおり。そのときは記録を作り直し、理由をその課題のレビュー記録に書く。
  - jsdom にはレイアウトがないので、遅延スクロールの位置は確かめられない。`setTimeout` で予約されることだけを記録し、位置は画面確認で見る。
- **配布物（IIFE）のテスト（新規・先に書く）**: ビルド済みの `dist/*.js` を jsdom の `<script src>` として評価し、
  - グローバル（`window.DatePicker.DatePicker` など）の構造。export されるのがクラス1つだけであること
  - 先に `window.DatePicker = { other: 1 }` があってもそのプロパティが残ること（`extend: true`）
  - 祝日 CSV の URL がスクリプトの場所から決まること（`/dist/datepicker.js` なら `/dist/holiday.csv`）
  - 読み込み中（DOMContentLoaded 前）と読み込み後の、どちらのタイミングでも自動初期化されること
  を確かめる。dist を使うので、最後にビルドしてから走らせる。
- **公開 API（新規・先に書く）**: 各エントリの export のキーが今と同じ（`['DatePicker']` など1つだけ）。static `instances` がクラスごとに別。
  利用者のサブクラス（`class X extends DatePicker { static instances = [] }`）のインスタンスが `DatePicker.instances` に入り、
  通常の DatePicker と互いに閉じ合うこと。TimePicker の公開メソッドがそろっていること。
- **切り出した関数の単体テスト（新規・先に書く）**: `tests/core/*.test.js`。今の正しい振る舞いだけを確かめる。
  既知のバグに当たる入力（`nearestTime` の繰り上がり、`minuteValues` に 0 や負の数、など）は固定しない。
  - date-utils: `parseDateOption`（null、'today'、Date、'2026-1-5'、不正な文字列）、`isOutOfRange`（両端を含む、時刻は無視）、
    `buildMonthCells`（42件、2026年2月は前月の残りなし、2028年2月は29日、年またぎ）、`formatDate`、`holidayKey`
  - time-utils: `HOURS`、`minuteValues(15)`・`(30)`、`nearestTime`（繰り上がらない範囲: 10:00、10:10→10:00、10:20→10:30）、
    `matchTimeValue`、`splitTimeValue`
  - holidays: `parseHolidayCsv`（CRLF、見出し行、空行）、`loadHolidays`（404・例外で空の Set）
- **先に失敗を確かめる**: 失敗を確かめるのは core の単体テストだけ（core がまだないので失敗する）。
  振る舞いの記録との比較、配布物のテスト、公開 API のテストは今の契約を基準にするテストなので、**共通化の前に今のコードで通ること**を確かめる
  （基準の作り方が正しいことの確認）。
- **最後にまとめて走らせる**: **ビルド → テスト全体**の順（配布物のテストが新しい dist を見るように）、
  その後に `dist` のサイズの記録、ブラウザでデモ3ページの画面確認。README の開発手順にも「テストの前にビルドする」と書く
  （開閉、日付・時刻の選択、祝日の表示、datetime の横並びの表示）。
