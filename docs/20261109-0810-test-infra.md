# テスト基盤と Docker 開発環境（DP-0015）

- ステータス: Reviewed
- 課題: LAP DP-0015「日付・時刻の計算ロジックに単体テストを追加する」
- 作成: 2026-11-09

## 1. 目的

このリポジトリには自動テストも、Docker の開発環境もない。レビューで見つかった残り14件（DP-0001〜0014）を
「再現テストを先に書く」手順で直すために、その土台を作る。

1. ホストで npm を使わずに、install・ビルド・テストを Docker の中だけで行えるようにする。
2. node:test と jsdom で、3つのピッカーの DOM の振る舞いを自動テストできるようにする。
3. DP-0010（3ファイルの共通化）の前に、今の正しい振る舞いを固定する特性テストを書く。

## 2. スコープ

### やること

- Docker 開発環境（`Dockerfile`、`compose.yaml`）
- テストの仕組み（`package.json` の `test` スクリプト、`tests/helpers/`）
- 3つのピッカーの特性テスト（今の正しい振る舞いだけ）
- 依存の更新（npm audit の high を解消）と jsdom の追加
- README に「開発」の節を追加、`CHANGE_LOG.md` を新規作成

### やらないこと

- 計算ロジックの関数への切り出しと、その単体テスト: DP-0010（共通化）と各バグ修正で行う。
  DP-0015 の課題本文にある「関数として切り出す」は DP-0010 の範囲として扱う。
- 既知のバグ（DP-0001〜0014）を再現するテスト: それぞれの修正のときに書く。
- CI（GitHub Actions など）、カバレッジの閾値、実ブラウザでの E2E テスト。

## 3. 設計

### 3.1 Docker 開発環境

`Dockerfile`:

```dockerfile
FROM node:24-bookworm-slim@sha256:01d566e8d94d8c619591d78652babfccd3c6992a3dffa9ed5ab39e11cf6c70e9
RUN mkdir -p /work/node_modules && chown -R node:node /work
USER node
WORKDIR /work
```

- イメージはダイジェストで固定する（タグの付け替えで中身が変わらないように）。Node 24 は LTS。
  jsdom 30.1.3 の engines（`^22.22.2 || ^24.15.0 || >=26.0.0`）を満たす（コンテナの Node は 24.22.2）。
- root ではなく `node` ユーザーで動かす。`/work/node_modules` を先に作って `node` の持ち物にしておき、
  名前付きボリュームの初期化でこの持ち主が引き継がれるようにする。

`compose.yaml`:

```yaml
services:
  install:          # 依存の取得だけ。ネットワークあり
    build: .
    environment: { TZ: Asia/Tokyo }
    volumes: [".:/work", "node_modules:/work/node_modules"]
    command: ["sh", "-c", "npm audit --audit-level=high && npm ci --no-fund"]
  dev:              # テスト・ビルド。ネットワークなし
    build: .
    environment: { TZ: Asia/Tokyo }
    network_mode: none
    volumes: [".:/work", "node_modules:/work/node_modules"]
volumes:
  node_modules:
```

- マウントするのはプロジェクトのディレクトリだけ（`~/.ssh` などはマウントしない）。
- `node_modules` は名前付きボリュームに置く。ホストにある macOS 用の `node_modules`（rollup のネイティブバイナリを含む）と
  混ざらないようにするため。ホストの `node_modules/` には触れない（.gitignore 済み）。
- ネットワークが要るのは `npm ci` だけなので、`install` サービスに分ける。テストとビルドは `network_mode: none` で動かす。
- `install` は `npm audit --audit-level=high` が通らなければ `npm ci` をしない（high 以上を無視しない規則を仕組みで守る）。

使い方（README に書く）:

```sh
docker compose run --rm install          # 依存を入れる（最初と lockfile の更新時）
docker compose run --rm dev npm test     # テスト
docker compose run --rm dev npm run build  # dist を作る
```

### 3.2 依存の変更

| パッケージ | 変更 | 理由 |
|---|---|---|
| 推移的依存（rollup 4.53.3→4.65.0、postcss 8.5.6→8.5.31、browserslist、nanoid、picomatch、svgo、source-map-js、yaml など） | `npm audit fix`（lockfile のみ、package.json の範囲内） | high 7件・moderate を解消 |
| `@rollup/plugin-terser` | `^0.4.4` → `^1.0.2`（メジャー更新） | 依存の serialize-javascript（high）を解消。peer の rollup `^4` を満たす |
| `jsdom` | `^30.1.3` を devDependencies に追加 | DOM の振る舞いを Node でテストするため |

- 版は `--before=2026-10-26` を付けて選び、公開から2週間以上たったものだけを使う（jsdom 31.0.0 は公開4日目なので使わない）。
- jsdom: 公式リポジトリ jsdom/jsdom、MIT、週間ダウンロード約1.5億、2026-11 時点でも更新が続いている。
  postinstall スクリプトはない（npm ci 後に `npm query ':attr(scripts, [postinstall])'` で確かめる）。
- 更新後に残る指摘は deepmerge（low 2件）。npm が示す修正は `@rollup/plugin-node-resolve` を 7.x に**下げる**もので、
  現行の 15.x から大きく戻ることになるため採らない。deepmerge は rollup の設定のマージに使われるだけで、入力は自分たちの設定に限られる。
- **受け入れ条件**: 依存の更新後に作った `dist/*.js` が、今のコミットの `dist/*.js` とバイト単位で同じであること
  （試作で確認済み。更新がビルド結果を変えないことの証拠にする）。

### 3.3 テストの仕組み

- テストランナー: Node 標準の `node:test` と `node:assert/strict`（追加の依存なし）。
- `package.json`:
  `"test": "node --import ./tests/helpers/register-css.js --test \"tests/**/*.test.js\""`
  （package.json は `"type": "module"` なので、`.js` はすべて ESM）
- ソースは `import './xxx.css'` を含み、Node はそのままでは読めない。
  `tests/helpers/css-loader.js` に Node のモジュールフック（`module.register` の `load`）を置き、
  `.css` を空のモジュールとして返す。`register-css.js` がこれを登録する。依存は増えない。
- `tests/helpers/dom.js`:
  - `setupDom(html, { url })`: JSDOM を作り、`window`・`document`・`Event`・`KeyboardEvent`・`MouseEvent`・
    `HTMLElement`・`Node` をグローバルに置く。`fetch` はスタブにする（祝日 CSV の中身を渡せる。既定は 404）。
    戻り値の `cleanup()` で、置いたグローバルを元に戻し、JSDOM を閉じる。
  - JSDOM には `VirtualConsole` を渡し、`jsdomError`（イベントハンドラ内の未処理例外など）を集める。
    jsdom はハンドラ内の例外を投げ直さず報告するだけなので、そのままでは値の検証が通ってしまう。
    `cleanup()` は集めたエラーが1件でもあれば例外を投げ、テストを失敗させる（各テストの `afterEach` で呼ぶ）。
  - `loadModule(name)`: `import('../../<name>.js?case=<連番>')` で毎回新しいモジュールとして読み込む。
    3つのモジュールは読み込み時に自動初期化を走らせ、クラスの static `instances` を持つので、テストごとに作り直す必要がある。
  - `settle()`: 自動初期化（fetch の Promise）が終わるまで待つ。
- 時刻: `node:test` の `mock.timers.enable({ apis: ['Date', 'setTimeout'], now })` で固定する。
  ソースは Node のグローバルの `Date`・`setTimeout` を使うので、これで「今日」と「現在時刻」が決まる。
- タイムゾーン: mock timers は時刻を固定するだけで、`getHours()` などのローカル解釈は TZ に依存する。
  compose で `TZ=Asia/Tokyo` を明示する。加えて、テストで固定する `now` は `new Date(2026, 0, 15, 10, 0)` のように
  ローカル時刻で組み立て、TZ が違っても期待値がずれないようにする。
- テストファイルは既定でファイルごとに別プロセスで動く（node:test の既定）。同じファイル内では、
  テストごとに `setupDom` と `loadModule` をやり直して独立させる。

### 3.4 特性テスト（今の正しい振る舞いを固定する）

DP-0010 の共通化で振る舞いが変わらないことを確かめるためのテスト。**既知のバグに当たる振る舞いは固定しない**
（例: 分の丸め、矢印キーで月をまたぐ移動、開いたときの書き込み）。

`tests/datepicker.test.js`（DatePicker）:
- `.date-picker-wrapper` が自動初期化される。data 属性（`min-date`/`max-date`/`format`）が反映される
- input のクリック・Enter で開き、Esc・外側クリックで閉じる
- 日付クリックで `YYYY/MM/DD`（または `data-format`）が入り、change が1回発火し、閉じる
- `minDate`/`maxDate` の外の日が disabled になる。min/max の当日は選択できる（境界を含む）。`today` 指定
- 祝日 CSV の日付に `holiday` クラスが付く
- 前月・次月ボタン、今日ボタン（範囲外なら何もしない）、クリアボタン
- 月の境界（正常系）: 平年と閏年の2月の日数（2026年2月は28日、2028年2月は29日）、
  12月から次月ボタンで翌年1月、1月から前月ボタンで前年12月、月末日（1/31）を表示中に次月で2月に進む（スキップしない）。
  矢印キーでの月またぎは既知のバグ（DP-0003）なので、ここでは固定しない
- 別のピッカーを開くと前のピッカーが閉じ、overlay は1つ
- `destroy()` で DOM・リスナー・overlay が片付く

`tests/timepicker.test.js`（TimePicker）:
- `.tp-input` が自動初期化され、`data-minute-step` の刻みで分の項目が並ぶ
- クリックで開き、時と分を選ぶと `HH:mm` が入る
- 既存の値があれば、その時・分が選択状態になる
- Esc で閉じる、overlay クリックで閉じる、別のピッカーを開くと前が閉じる

`tests/datetimepicker.test.js`（DateTimePicker）:
- mode ごとの DOM（date / time / datetime）
- date モード: DatePicker と同じ観点（上の DatePicker の項目を同じヘルパーで流す）
- time モード: 時・分の選択で `HH:mm`
- datetime モード: 日付を選んでも閉じない。日付と時刻で `YYYY/MM/DD HH:mm`。クリアで空になる
- `destroy()`

`tests/infra.test.js`（仕組み自体の確認）:
- `.css` の import が空のモジュールとして読める
- `loadModule` を2回呼ぶと別のモジュール（static `instances` が独立）になる
- イベントハンドラ内で例外を投げると、`cleanup()` がそれを検出して例外を投げる

## 4. テスト方針

- **何を確かめるか**: 3.4 の特性テストで、今の正しい振る舞い。既知のバグは各修正のときに再現テストを足す。
- **どう走らせるか**: `docker compose run --rm dev npm test`（ネットワークなしのコンテナ）。ホストでは走らせない。
- **先に失敗を確かめる**: テストファイルとヘルパーを書いた時点で、依存（jsdom）と `test` スクリプトがないため失敗する。
  その後に依存と仕組みを入れて通す。特性テストは今のコードの振る舞いを書くので、仕組みが入れば通るのが期待どおり。
  1件でも落ちたら、テストの誤りか、見落としていたバグかを調べる（期待値は緩めない）。
- **時刻**: mock timers で固定し、TZ も明示して、実行日・時刻・環境で結果が変わらないようにする。
- **例外**: jsdom 内の未処理例外は `cleanup()` でテスト失敗にする（値が正しくても例外があれば失敗）。
- **ビルド**: `dist/*.js` が今のコミットとバイト単位で同じことを `cmp` で確かめる（3.2 の受け入れ条件）。
- **画面の確認**: dist が同じなので、この課題では不要。DP-0010 以降で行う。
